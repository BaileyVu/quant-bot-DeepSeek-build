C. Market Data Path
Uses the existing LiveMarketData class (Milestone 1) which connects to Binance WebSocket (wss://stream.binance.com:9443/ws) and listens for kline_1m streams. Each completed candle is passed to the runtime via callback.

D. Candle Processing
Only completed candles (kline x == True) are processed.

Duplicate detection: tracks last processed timestamp per symbol; any candle with timestamp <= last is ignored.

Validation uses the same validate_candle from Milestone 1.

E. Feature Pipeline
Reuses the exact FeatureEngine from Milestone 2, with the same feature set (13 features). Features are computed on the fly from the accumulated history buffer (last 100 candles). The same compute_features method is used.

F. Model
Loads the saved model artifact from data/parquet/models/<symbol>/<version>/model.pkl. Uses the exact feature names and ordering from training. No retraining or modification.

G. Signal Path
Model prediction (probability of class 1) is used directly as the signal. If signal >= threshold (0.5 by default), entry is triggered; otherwise exit.

H. Risk Path
The RiskEngine checks:

Notional value of the order does not exceed max_position_notional (configurable).

Current drawdown from peak equity does not exceed max_drawdown_pct.
(More checks can be added but these are the MVP.)

I. Paper Execution
Simulated execution uses the same accounting as Milestone 4:

Entry: buys with all available cash, applies fee and slippage.

Exit: sells entire position, applies fee and slippage.

Trades are recorded with full details.

J. Portfolio
Multi‑symbol portfolio with shared cash.

Positions are stored in a dict keyed by symbol.

Equity = cash + sum(position * mark price). Mark price is the latest candle close.

Trades list and history snapshots are maintained.

K. Persistence
State is saved to data/paper/paper_state.json after each candle (and on shutdown). It includes cash, positions, entry prices, trade list, last processed timestamp, and history buffer.

L. Safety Barrier
The SafetyBarrier class raises a RuntimeError if any order‑submission method is called in paper mode. It is instantiated and checked at the beginning of the runtime; any attempt to call a real Binance order endpoint would be intercepted. Additionally, the paper runtime never instantiates a Binance trading client; only the public market‑data WebSocket is used.

M. Failure Handling
Stale data: If no new candle arrives within stale_data_timeout_seconds, a warning is logged and no new decisions are made (the loop continues monitoring but stops trading).

Disconnect: The underlying LiveMarketData attempts to reconnect automatically (basic retry logic not implemented in detail, but the WebSocket library will reconnect; we can add a simple retry in the loop if needed).

Invalid candle: Ignored with a warning.

Model failure: If model loading fails, the runtime raises an exception and does not start.

Accounting failure: If portfolio cash becomes negative or equity non‑finite, the runtime logs an error and stops (could be enhanced).

P. Known Limitations
The runtime does not handle multiple symbols simultaneously in the same process (it is single‑symbol). It can be extended by running separate processes or by modifying the runtime to handle multiple streams.

Reconnection logic is basic – relies on the WebSocket library; we do not implement exponential backoff.

The risk engine is minimal (only notional and drawdown limits); more sophisticated risk (e.g., daily loss, correlation) is not implemented.

Persistence does not include feature history buffer restoration fully (we store history buffer as list of candles, but not the exact feature DataFrame). This could be improved.
